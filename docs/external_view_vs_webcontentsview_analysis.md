# 다중 창 환경: 내장 뷰(WebContentsView) vs 외부 뷰(OS Window) 장단점 분석

사용자님께서 제안하신 **"Electron의 순정 내장 뷰(WebContentsView)를 완전히 포기하고, 4개의 창 모두를 별도의 외부 뷰(독립된 Chrome/Patchright 윈도우)로 운영할 경우"**에 대한 기술적 장단점을 심층 분석합니다.

여기서 '별도의 뷰'란, Electron 앱 내부의 HTML/DOM 요소가 아니라, 윈도우 운영체제(OS)가 띄우는 **진짜 크롬 브라우저 창 4개**를 뜻하며, 이를 Win32 API 등을 이용해 Electron 앱 위에 퍼즐처럼 끼워 맞추는(Docking/Overlay) 방식을 의미합니다.

---

## 1. 별도의 뷰 (외부 OS 윈도우) 사용 시의 장점 (Pros)

### 1) 절대적인 스텔스(Stealth) 보장
- **설명**: 4개의 창 모두가 순정 Electron 엔진과 완전히 격리된, 독립적인 크롬(또는 Patchright 개조 엔진)으로 구동됩니다.
- **효과**: 향후 구글 Flow AI나 기타 2개의 사이트가 유튜브급의 강력한 봇 탐지 시스템을 도입하더라도, 어떠한 추가 작업 없이 100% 탐지를 회피할 수 있습니다. 스텔스 관점에서는 이견이 없는 **'가장 완벽한 무적의 방어력'**을 갖게 됩니다.

### 2) 네이티브 렌더링 성능 (CPU 최적화)
- **설명**: Canvas Screencast 기법처럼 화면을 캡처해서 JPEG로 쏘아줄 필요가 없습니다. 각 창이 자체적으로 GPU 가속을 받아 화면을 그립니다.
- **효과**: 시스템 CPU와 메모리 오버헤드가 극도로 낮아지며, 동영상 재생이나 무거운 WebGL 사이트 접속 시 화면이 끊기지 않는 최고의 퍼포먼스를 보여줍니다.

### 3) 구조의 극단적 단순화 (Decoupling)
- **설명**: 파이썬 백엔드가 Electron을 거치지 않고 4개의 크롬 창과 직접 통신(CDP)합니다. 
- **효과**: Electron 앱은 단순히 '버튼을 누르는 리모컨' 역할만 하므로, 브라우저 자동화 로직과 데스크톱 UI 로직이 완벽하게 분리되어 유지보수가 매우 쉬워집니다.

---

## 2. 별도의 뷰 (외부 OS 윈도우) 사용 시의 단점 (Cons)

스텔스는 완벽해지지만, 사용자님께서 요구하셨던 **"위치와 크기가 유동적으로 바뀌는 4개의 다중 창 UX"**를 구현함에 있어 **치명적이고 파괴적인 UI/UX 붕괴**를 감수해야 합니다.

### 1) 레이아웃 고스팅(Ghosting) 및 화면 찢어짐
- **증상**: Electron 앱의 메인 창 크기를 마우스로 잡고 늘리거나 줄일 때, 안에 끼워져 있던 4개의 외부 윈도우가 그 속도를 따라가지 못합니다.
- **결과**: 앱 창과 내부 뷰어들이 따로 노는 현상(화면이 밀리거나 투명한 배경이 노출되는 찢어짐 현상)이 무조건 발생합니다. 사용자에게 '매우 조잡하게 만들어진 프로그램'이라는 인상을 줍니다.

### 2) Z-Order 붕괴 (모달 창 및 드롭다운 가림 현상)
- **증상**: 외부 윈도우는 OS 레벨에서 항상 최상단(Top)을 차지하려는 성질이 있습니다.
- **결과**: ViraLoop 앱의 상단 메뉴바(Menu)를 클릭하거나, 세팅 팝업(Modal)을 띄웠을 때, 이 팝업 창이 **4개의 크롬 창 뒤로 숨어버려서 클릭할 수 없는 치명적 버그**가 발생합니다. 이를 막으려면 팝업을 띄울 때마다 4개의 크롬 창을 강제로 숨김(Hide) 처리해야 하는 끔찍한 로직이 필요합니다.

### 3) 윈도우 OS 종속성 (Cross-Platform 불가)
- **증상**: 4개의 외부 창을 빈틈없이 끼워 맞추려면 윈도우 운영체제 전용 API(`SetParent`, `MoveWindow` 등)를 무겁게 사용해야 합니다.
- **결과**: 코드가 Windows OS에 영구적으로 종속됩니다. 추후 macOS나 Linux용 버전을 출시하려면 화면 렌더링 로직 전체를 아예 밑바닥부터 새로 짜야 합니다.

### 4) 포커스 뺏김 현상 (Focus Stealing)
- **증상**: 하나의 프로그램 안에서 4개의 독립된 프로세스 창이 돌아가므로, 창 사이를 마우스로 오갈 때 윈도우의 '활성 창(Focus)'이 계속 바뀝니다.
- **결과**: 타이핑을 치다가 포커스가 다른 창으로 날아가는 등 UX가 매우 산만해집니다.

---

## 3. 최종 요약 및 판단 (Verdict)

| 평가 항목 | Electron 내장 뷰(WebContentsView) | 외부 뷰(OS 윈도우)로 교체 시 |
| :--- | :--- | :--- |
| **스텔스 (봇 탐지 회피)** | 유튜브 1개만 완벽 방어 (나머지 3개 무방비) | **4개 창 모두 100% 무적 방어 (압승)** |
| **다중 창 UI 유동성 (리사이징)** | **매우 부드럽고 자연스러움 (압승)** | 화면이 덜덜거리고 찢어짐 (최악) |
| **앱 내 팝업/모달창 호환성**| **완벽 호환 (압승)** | 모달 창이 뷰 뒤에 숨어버림 (최악) |
| **운영체제 호환성** | **Windows, Mac 모두 동일 작동 (압승)**| Windows 전용 API 종속 (Mac 불가) |

**💡 결론:**
"별도의 뷰(외부 OS 윈도우) 4개"를 사용한다는 것은, **"디자인과 UX의 부드러움을 완전히 포기하는 대신, 앞으로 어떤 봇 탐지 시스템이 들어오든 절대 막히지 않는 무적의 탱크를 만드는 것"**과 같습니다.

만약 ViraLoop Studio가 **"투박하고 화면이 좀 찢어지더라도 자동화의 안정성이 절대적인 1순위"**라면 외부 뷰를 채택하는 것이 맞습니다. 

하지만 **"프리미엄 데스크톱 앱으로서의 부드러운 사용성과 미려한 다중 창 UI"**를 중요하게 생각하신다면, 이전의 Path G(유튜브 1개만 스트리밍하고 나머지는 내장 뷰 사용)가 여전히 최선의 타협점입니다.
